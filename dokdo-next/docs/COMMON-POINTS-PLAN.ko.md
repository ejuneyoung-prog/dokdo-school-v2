# 배움터·놀이터 공통 활동포인트 설계 초안

2026-10-19 · 교수님 검토용 · 설계만 작성, 적립·교환 기능 활성화 없음

독도 배움터와 독도 놀이터에서 쌓은 활동을 한 계정의 공통 활동포인트로 이어 보여 줍니다. 기존 학습 성취와 게임 기록은 보존합니다. 굿즈·상품점 연결은 이후 별도 결정하며, 지금 포인트 환산율·상품 가격·교환 가능 시점을 약속하지 않습니다.

## 1. 현재 기록과 앞으로의 관계

| 구분 | 현재 확인한 동작 | 공통포인트 도입 후 |
| --- | --- | --- |
| 학습 XP | 같은 개념의 당일 첫 보상 대상 정답에 10 XP. 재시도 정답·건너뛰기·진단은 XP 없음 | 기존 숫자·적립 규칙 유지. 포인트와 합산·차감하지 않음 |
| 학습 진도·학년 | 단원 완료·복습 근거·불빛은 학습 기록. 학년 계산은 문항별 첫 정답 1, 반복 정답 0.5에 기반 | 포인트 사용으로 진도·학년·불빛이 내려가지 않음 |
| 게임 점수·최고 기록 | 바다 청소 점수, 달리기 점수·도달 라운드. 브라우저에 저장 | 도전 성취로 계속 보존. 점수 자체를 결제 수단으로 쓰지 않음 |
| 꾸미기 XP | 게임 누적 점수의 `floor(점수/10)`을 한 판에서 중복 지급 없이 반영. 꾸미기 레벨·선물에 사용 | 기존 레벨·선물·획득 XP 보존. 상품 교환으로 빼지 않음 |
| 현재 두 영역의 연결 | 배움터의 재시도가 아닌 정답과 놀이터 도전권 퀴즈가 같은 개념의 일일 보상을 공유: 도전권 1회·꾸미기 XP 5. 두 게임은 기본 도전권 하루 3회를 공유 | 이 연결은 유지. 같은 학습 활동을 두 영역에서 제출해 공통포인트가 두 번 생기지 않게 함 |
| 공통 활동포인트 | 아직 없음 | 서버가 확인한 이후 활동만 계정 원장에 적립. 두 영역에 같은 잔액 표시 |
| 명예의 전당·공개 순위 | 기존 학습 서버·공개 응답 체계 사용 | 공통포인트와 분리. 기존 점수·집계·공개 범위 변경 없음 |

화면에는 ‘학습 진도’, ‘내 최고 기록’, ‘꾸미기 레벨’, ‘활동포인트’를 서로 다른 값으로 표시합니다. 활동포인트는 ‘지금 쓸 수 있는 잔액’과 ‘누적 획득’을 구분합니다. 소비하더라도 누적 획득과 학습 성취는 남습니다.

현재 근거: `assets/app-model.js`의 `answer`, `assets/dokdo-core.js`의 `gradeScore`, `assets/games-core.js`의 `rewardLearning`·`checkpoint`, `assets/games-entry.js`의 학습 보상 연결. 이는 현행 동작 설명이며 새 환산율 제안이 아닙니다.

## 2. 계정 원장과 검증 흐름

교수님 소유 Supabase 서울 프로젝트 `cqlvhrodebmhxbrhlmzu` 생성은 완료됐습니다. 실제 회원·SMTP 설정은 진행 중이며 공통포인트 원장과 자동 동기화는 연결하지 않았습니다. 별명이 아닌 인증된 계정의 `auth.uid()`를 소유자로 사용합니다.

1. 서버가 로그인 계정을 확인하고 활동 ID, 적용 규칙 버전, 만료 시각을 발급합니다. 브라우저가 보낸 정답 여부·최종 점수·휴대전화 시각만으로 적립하지 않습니다.
2. 학습은 서버가 문항·선택 답·개념·재시도 여부를 확인합니다. 게임은 서버가 발급한 실행 ID·난수 기준·입력 이력 등을 서버 규칙으로 재검증합니다. 이를 구현하기 전 게임 점수는 꾸미기용으로만 남기고 실물 보상 포인트를 지급하지 않습니다.
3. 확인된 활동에만 서버가 포인트를 결정합니다. 계정별 일일 한도와 활동별 보상 조건은 한국 시간 기준으로 서버에서 검사합니다. 오프라인 활동은 ‘확인 대기’이며 교환 잔액에 넣지 않습니다.
4. 원장은 추가 방식으로 기록합니다. 기본 항목은 `entry_id`, `user_id`, `event_key`, `source_activity_id`, `rule_version`, `kind`, `delta_available`, `delta_reserved`, `created_at`, `reference_entry_id`입니다. 이벤트 키에 계정·원본 활동·보상 종류를 묶고 데이터베이스 고유 제약으로 중복을 막습니다. 같은 요청을 재전송하면 기존 처리 결과를 돌려줍니다.
5. 배움터와 놀이터 퀴즈의 동일 개념 보상은 영역명이 아닌 공통 활동 식별자를 씁니다. ‘개념별 하루 1회’ 같은 적립 조건은 교수님 확정 후 적용합니다. 오류 수정·취소는 원본을 고치거나 지우지 않고 참조 항목을 추가해 상쇄합니다.

브라우저는 자기 원장만 읽습니다. 적립·차감·한도 판단은 서버 전용 함수에서 처리하며 클라이언트의 원장 직접 INSERT/UPDATE/DELETE는 허용하지 않습니다. 읽기는 `auth.uid() = user_id`인 RLS로 제한하고 비밀키는 서버에만 둡니다. 잔액은 원장으로 계산하며, 별도 빠른 조회값을 두더라도 원장과 대조할 수 있어야 합니다. 현재 준비된 비공개 백업 테이블은 포인트 원장으로 재사용하지 않습니다.

## 3. 향후 교환을 붙일 때 지킬 처리 순서

지금 상품점·재고·배송·연락처 수집·결제는 추가하지 않습니다. 다음은 이후 기능을 승인받았을 때 구현할 원칙입니다.

- 교환 신청 시 서버가 확정된 교환 조건과 잔액을 확인합니다. 계정 단위 잠금과 한 번의 DB 트랜잭션으로 교환 ID 발급·중복 요청 확인·잔액 예약을 함께 처리합니다. 두 기기에서 동시에 신청해도 같은 잔액을 두 번 쓰지 못하게 합니다.
- 예를 들어 P포인트를 예약하면 가용 잔액 `-P`, 예약 잔액 `+P`; 교환 확정 시 예약 잔액 `-P`; 실패·취소 시 가용 `+P`, 예약 `-P`를 원장에 남깁니다. 처리 전후 가용·예약 잔액은 음수가 될 수 없습니다. 확정·취소 재시도도 같은 교환 ID로 한 번만 처리합니다.
- 현금 가치·현금 환급·교환 보장을 표시하지 않습니다. 공급·취소·환불 정책과 필요한 최소 정보·보관 기간은 실제 상품 연결 전에 별도로 정합니다. 배송 정보가 필요해지는 시점에도 활동 원장·공개 순위에 섞어 저장하거나 노출하지 않습니다.
- 기존 브라우저 XP·게임 점수·업로드한 과거 백업은 쉽게 수정될 수 있으므로 실물 보상 포인트로 자동 환산하지 않습니다. 기존 성취는 그대로 보존하고 ‘이전 기기의 성취’로 구분합니다. 소급 인정이 필요하면 교수님이 별도의 검증·인정 방식을 결정합니다.

## 4. 실행 순서와 승인할 사항

① 계정·SMTP와 자기 기록 접근 보호 검증 → ② 두 영역에서 같은 계정·잔액을 읽는 화면 → ③ 서버 검증 활동·원장·중복 방지 구현 → ④ 실제 교환 없이 적립 검수 → ⑤ 교수님 승인 후 적립 공개 → ⑥ 별도 승인 후 상품 연결 순서로 진행합니다. 검수에서는 두 기기 동시 제출, 같은 요청 재전송, 자정 경계, 취소 중 재시도, 타인 원장 접근 거부, 조작한 로컬 점수의 적립 거부를 확인합니다.

교수님 결정이 필요한 항목: 포인트 명칭, 활동별 적립률·반복/복습 인정·일일 한도, 소급 인정 여부와 근거, 사용/만료 정책, 교환 조건과 운영 책임, 계정·활동 정보 저장 범위입니다. 미결정 항목은 활성화하지 않습니다. 이번 문서는 기존 학생 기록·문항·공개 순위 규칙·운영 Apps Script를 변경하지 않습니다.
