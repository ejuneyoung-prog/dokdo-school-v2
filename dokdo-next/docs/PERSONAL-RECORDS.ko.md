# 내 독도 성장 기록 · 2026-10-19

## 이번 구현과 운영 상태

로그인 페이지 아래에 학습·게임·꾸밈의 기기 기록을 세 카드로 모읍니다. 학습과 게임 XP는 합산하지 않습니다. 실제 저장된 섬·강치·최고 라운드 및 점수만 표시합니다. 세 버튼은 배움터(?area=learn), 게임(#games), 꾸미기(#island)로 바로 이동합니다. 별도 회원 정보 입력은 늘리지 않습니다.

privateRecordsEnabled:false가 기본입니다. 현재 운영에서는 기기 기록 표시만 사용하며, 계정 간 보관·다른 기기 이어하기는 아직 활성화하지 않았습니다. 로그인 성공은 기록 동기화 성공을 뜻하지 않습니다.

계정 보관 구현은 초기부터 자동 합치기를 하지 않습니다. 본인 기록 확인 체크 → ‘내 계정에 저장’으로 현재 학습·게임 스냅샷을 저장합니다. 다른 기기에서는 계정 기록 요약을 보고 ‘계정 기록으로 이어하기’ → 복구 사본을 먼저 남기고 적용합니다. 현재는 수동 저장이며, 자동 동기화로 표시하지 않습니다. 이것은 공용 기기의 학생 기록이 엉뚱한 계정에 붙는 위험을 막기 위한 첫 단계입니다.

향후 명시적으로 연결한 개인 기기에 한해 자동 저장을 추가할 수 있습니다. 자동 저장 도입은 이번 구현 범위가 아니며 아직 동작하지 않습니다. 회귀 보상·순위 규칙·굿즈 교환은 그대로 유지합니다.

## 개인정보 및 기록 경계

계정 보관함에는 닉네임·국가·학교(기존 선택값), 문항별 학습 진도, 꾸민 섬·게임 기록이 들어갑니다. 가입 이메일/비밀번호·Supabase 세션·토큰·기존 복구 번호는 스냅샷에 넣지 않습니다. 사용자 ID와 서버 revision은 별도 기기 키에만 기록하고 학습·게임 state 또는 기존 운영 Sheet로 보내지 않습니다. 기존 V1/V2·공개 응답/명예의 전당·학생 공개 범위는 변경하지 않습니다.

기기에서 로그아웃은 이미 이 브라우저에 남아 있는 학습·게임 기록을 지우지 않습니다. 공용 기기에서는 다른 사람 기록일 수 있음을 로그인 전후에 명시합니다. 닉네임만 보고 계정을 합치지 않습니다. 개인 기록 보관 버튼은 운영자 DB 검증 후에만 활성화합니다.

전송용 상태는 두 진행 키만 읽고, 허용한 필드만 복사합니다. 개념별 주간 중복 인정 방지 키와 기존 선물 legacy를 보존합니다. 손상/새 형식/용량 초과를 원본을 지우고 초기화하는 방식으로 처리하지 않습니다.

## 서버와 경합 제어

- docs/private-records.sql은 새로운 private table과 자기 행 SELECT RLS를 만듭니다. 익명/직접쓰기 권한은 회수하고, auth.uid()를 사용하는 RPC만 저장합니다. Apps Script·기존 시트는 변경하지 않습니다.
- RPC는 현재 revision과 정확히 일치할 때만 원자적으로 UPDATE하며, 최초 INSERT 중복은 충돌입니다. 단순 upsert로 덮지 않습니다. 사용자 ID는 요청 인수로 받지 않습니다.
- 요청마다 getSession의 토큰과 getUser(token)의 ID를 검증하고, 이 토큰으로 Authorization이 고정된 비영속 API 클라이언트를 씁니다. 전환된 계정의 최신 토큰으로 이전 계정 기록을 잘못 보내지 않습니다. UI 세대 검사로 늦은 응답을 폐기합니다.
- 복원은 Web Locks의 학습/게임 쓰기 잠금을 둘 다 얻고 원본 두 값을 비교한 뒤, 별도 키의 완전한 복구 사본이 저장·확인된 경우에만 진행합니다. 두 번째 쓰기가 실패하면 가능한 첫 쓰기를 되돌리고 복구 사본을 남깁니다. 다른 창 변경이나 기존 진행 중 게임이 있으면 중지합니다.
- 진도·점수·선물을 잃거나 서로 다른 프로필이 충돌하는 복원은 거절합니다. 자동 최대값 합산은 하지 않습니다.
- 설정/개인 기록 UI가 실패해도 기존 이메일 로그인은 초기화되어야 합니다. 새 기록 저장소는 계정 화면에서만 접근하며 메인/놀이터에는 SDK·새 서버 요청을 추가하지 않습니다.

## 마지막 운영 절차

1. 교수님 승인 후 Supabase SQL Editor에서 private-records.sql을 실행합니다(새 개인 보관함만 생성, 기존 데이터 무수정).
2. private-records-verification.sql을 실행해 가상 A/B 사용자와 익명 접근·CAS·직접쓰기 차단을 확인합니다. 이 검사는 트랜잭션 끝에서 가상 사용자와 기록을 전부 rollback합니다. 실제 학생을 쓰지 않습니다.
3. 운영자의 실제 계정으로 저장·다른 기기 복원·로그아웃·계정 전환을 확인한 뒤 privateRecordsEnabled:true를 배포합니다. 검증 전에는 false입니다.

JS 가짜 SDK·정적 SQL 검사는 실제 Postgres/RLS 검사를 대신하지 않습니다. 실제 DB 검사 결과는 활성화 시점에 별도로 기록합니다. 새 개인정보 목적·보관/삭제 운영 안내는 교수님 최종 확인이 필요합니다.
